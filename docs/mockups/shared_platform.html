Hosting plan · for review

One VM for many small apps

Grow the Flapjaw-only server into a small shared platform: one Hetzner VM with k3s, one Postgres cluster, and each app in its own namespace with its own database. Flapjaw is the first app on it.

DNS

One wildcard record, *.apps.<domain>, points at the VM. A new app needs no DNS change; a custom domain is one more record.

Hetzner Object Storage

postgres/: continuous backups of the whole cluster. dumps/<app>/: a nightly dump per app. Both kept 14 days.

Registries

Each app pushes its images to GitHub Container Registry (or any registry, with a pull secret in its namespace).

From Flapjaw's branch, infra/hetzner/ and the cluster-wide parts of deploy/ (cert-manager, the issuer, its own Postgres and backup job) move to platform. What stays is what runs in app-flapjaw.

VM size: 8 GB to start

One Hetzner x86 VM, for example CX32 or CPX31, about €8–15 a month (check Hetzner's price list). It grows in place with a rescale, or a second k3s node can join the same cluster.

Estimates, measured once the platform runs. Each app gets a quota (by default 512 MB requested, 1 GB at most), so one app can't starve the others.

The shared database

Recommended at 8 GB

CloudNativePG

One Postgres cluster declared in platform/cluster/postgres.yaml. The operator handles backups, point-in-time restore and upgrades. Each app's database and role are declared too.

Isolation inside Postgres

Each role owns only its own database. Connecting is revoked from everyone else. No app is superuser. Each role has a connection limit (20) and a statement timeout (30 s), so one app can't take every connection.

Two kinds of backup

Continuous backups restore the whole cluster to any minute. A nightly dump per database restores one app without touching the others.

Other engines

An app that needs MySQL or Redis runs it in its own namespace, inside its own quota. Only Postgres is shared.

Flapjaw needs one change for this

Its migrations create the roles anon, authenticated and service_role, and today the server runs as the database's owner. Roles are global across a Postgres cluster, so the platform creates those three once, and Flapjaw's server runs as an ordinary role that may change only its own database. Its tests get a mode that runs this way, so it is proven before the move.

What each app gets

One command in the platform repo, tools/new-app.ps1 <name> <host>, sets it all up.

A namespace with limits

app-<name>, with a memory quota and default limits for any container that forgot them.

Network rules

Only Traefik reaches it, plus cert-manager's check while a certificate is issued. It reaches only its own database, DNS and the internet.

Its database

A database, a role and a Secret with DATABASE_URL, pointing at the shared cluster.

Deploy rights for that app only

A kubeconfig that reaches only its own namespace. An app's deploy can never touch another app or the platform; your admin kubeconfig stays for the platform.

A host

<name>.apps.<domain> works at once through the wildcard record, with a certificate from the shared issuer.

The same deploy as Flapjaw

Images pinned to the git commit, kubectl apply -k, wait for the rollout, smoke test, rollback. Only the cluster pieces are gone.

GitOps and monitoring

Flux from the third app

With one app the deploy script was enough. With several, Flux (about 150 MB) keeps the cluster in sync with the platform repo and each app's deploy files; the scripts then only build images and bump the tag in git. Argo CD does the same with a web UI, for about 500 MB.

Light monitoring

metrics-server back on (about 50 MB, so kubectl top works) and an outside uptime check on every app's health URL. A full Prometheus and Grafana would cost more memory than the apps; leave it until something needs it.

Steps 1 to 4 are code and tests on your PC. Step 5 is yours: no Claude session creates accounts, VMs or DNS records.

Open questions for you

  1. Which other appsRoughly what they run (language, Postgres or something else), how much memory, and whether they need staging too. That decides whether 8 GB is enough.
  2. A separate platform repositoryOr a platform/ folder in one of the app repos? A separate one is recommended.
  3. The domainWhich domain gets the wildcard (*.apps.<domain>), and is it fine that every app shows up under it by default?
  4. CloudNativePG or plain PostgresCloudNativePG restores to any minute (recommended at 8 GB). A plain Postgres with nightly dumps per database is simpler and lighter, but restores only to last night.
  5. Flapjaw's launchLaunch Flapjaw on the shared VM, or on its own 2 GB VM first and move it over later? The deploy files differ only in the cluster pieces, so either works.
