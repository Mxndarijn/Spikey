Architecture, today and proposed

Today every server call goes through one class, SupabaseClient: a session plus call_db(name, body), which posts to a Postgres function. The game never reads a table directly. The proposal adds one interface below the existing services, so the screens and services do not change.

Where it runs: its own Hetzner VM with k3s

The game gets its own Hetzner VM, apart from your other application, running k3s as a one-node cluster that you manage with kubectl. Everything lives in the namespace flapjaw. k3s ships the Traefik ingress controller, so the only add-on is cert-manager with a Let's Encrypt ClusterIssuer (HTTP-01). The API host stays a placeholder, api.<your-domain>, until you pick one. If the game ever needs more machines, a second k3s node joins the same cluster.

Backups

Recommended

Object storage

A CronJob runs pg_dump every night and uploads it to a Hetzner Object Storage bucket, keeping 14 days. The copy lives off the VM, so it survives losing the VM, its disk or the namespace. Restore: psql the dump into a fresh Postgres.

A Hetzner volume

Cheaper and simpler, but the dumps sit next to the database: a deleted volume, a broken VM or a wrong kubectl delete can take both. Fine as a second, local copy.

The replay check on the server

Rust checks every run

The server links tools/fastsim-rs/sim and replays each run as it arrives, in a background queue. The check already holds the Rust copy tick for tick to GDScript (the parity step).

Godot decides rejections

A run Rust rejects is final only when headless Godot (server/verify_batch.gd) agrees. Rejections are rare, so this costs little, and a parity slip can never hide an honest score.

Older app versions

One frozen sim crate per allowed gameplay version (sim_g24, sim_g25, ...), dispatched on gameplay_version. Retired versions answer "please update".

Same outcomes

ok, rejected, outdated and pending keep today's rules and reasons, so boards behave the same, only faster.

Easier later on our own server: one-time seeds for endless runs, rate limits per player and IP, plausibility checks into a review queue, Play Integrity / App Attest on sign-in.

VM size: 2 GB by default

The plan fits on a 2 GB VM if every pod has a memory limit, the Godot check only runs when needed, Postgres is tuned small and the VM has swap as a safety net. 4 GB is the comfortable option: room for a staging copy beside prod, and no tuning to watch. The price gap between the two is small, so check Hetzner's list before choosing. Keep to x86 types; ARM would need arm64 builds of the server and of Godot.

Swap

cloud-init makes a 2 GB swap file with vm.swappiness=10, and k3s's kubelet is set to allow it (fail-swap-on=false). Swap is a safety net for a spike, not working memory.

Limits on every pod

Every container in deploy/ has a memory request and limit, so one pod that grows is restarted on its own instead of starving Postgres or k3s. A check in the deploy script refuses a manifest without them.

Staging on 2 GB

A second Postgres and API add about 250 MB. On 2 GB, staging runs only while you test and is scaled to 0 after; on 4 GB it can stay up.

Estimates

The numbers are typical sizes, not measurements. Step 3 of the rollout measures the real ones on a test VM and adjusts the limits.

Infrastructure as code

The VM and everything on it are described in the repo, so the game is always deployed the same way and can be rebuilt from nothing. Three parts: OpenTofu makes the VM, Kustomize describes what runs on it, and one script does every deploy.

1 · The VM: OpenTofu

infra/hetzner/ with the hcloud provider: the server (type, image, location), a firewall (80 and 443 open; SSH and the Kubernetes API only from your IP), the Postgres volume and the DNS record for api.<domain> (Hetzner DNS, or wherever the domain lives). A cloud-init.yaml installs k3s (metrics-server off, swap allowed), makes the swap file and copies nothing secret. The state file goes in a Hetzner bucket (S3 backend), so losing your PC loses nothing; a local, git-ignored state file works too.

2 · On the cluster: Kustomize

deploy/base/ holds the namespace, the server Deployment, the Godot check and backup CronJobs, Service, Ingress, the Postgres StatefulSet, NetworkPolicy, and cert-manager (its release manifest at a pinned version) with the ClusterIssuer. deploy/overlays/staging and deploy/overlays/prod set the namespace, host, sizes and image tag. Images are always pinned to the git sha, never latest.

3 · One deploy script

tools/deploy.ps1 -Env prod runs the same steps every time: refuse a dirty tree, build and push the image tagged with the git sha, set that tag in the overlay, run database migrations as a Job, kubectl apply -k deploy/overlays/prod, wait for kubectl rollout status, then a smoke test (/v1/ping answers that sha and the gameplay version). -Rollback redeploys the previous sha; -Sha <sha> deploys any earlier one.

4 · Secrets: env files

.env.staging and .env.prod stay on your PC, git-ignored. Kustomize's secretGenerator turns them into Secrets with a content hash in the name, so a changed secret restarts the pods that use it. .env.example lists every key.

Database migrations

Forward only, and each one works with the previous server version, so -Rollback never needs to undo a migration.

GitOps later?

Argo CD or Flux would sync the cluster from git by itself. For one VM and one person deploying, not yet: it costs a few hundred MB of the 2 GB and is one more thing to upgrade, and the script already makes every deploy the same. Worth it once there are more environments, more people, or deploys from CI.

Rebuilding from scratch if the VM dies

  1. 1
    About 5 minutes

    tofu apply

    A new VM, firewall, volume and DNS record; cloud-init installs k3s. Copy the kubeconfig from the VM.

  2. 2
    About 5 minutes

    tools/deploy.ps1 -Env prod

    cert-manager, Postgres (empty), the server and the CronJobs, the same sha as before. Let's Encrypt issues a new certificate.

  3. 3
    Minutes

    tools/restore.ps1 -Env prod

    Scales the server to 0, downloads the newest dump from the bucket, loads it into Postgres, scales the server back up.

  4. 4
    Check

    Smoke test

    The deploy script's smoke test plus a board load. At most a day of runs is lost (since the last nightly dump). The whole path is rehearsed once on staging before the cutover.

Rollout

BuildOn the cluster, debug buildsCutoverRetire

With a fresh start there is no data to copy and no freeze. Supabase keeps running untouched until the switch-off, so it is the rollback the whole way.

  1. 1
    Build · no server

    BackendClient interface, update prompt, one-time reset

    SupabaseClient implements the interface; the config picks the backend. A minimum-version answer the game shows as "please update" (today's builds have no such prompt). The one-time local reset, switched off until the cutover build (see below). No other behaviour change, check passes.

    Rollback: revert the commits.

  2. 2
    Build · local only

    Server skeleton

    Auth with device key, ping, submit_run, get_board, get_run, set_player, the Rust checker. Contract fixtures pass against both the SQL (via tools/db_test.ps1) and the new server.

    Rollback: nothing live yet.

  3. 3
    Build · local only

    The rest of the features, and the manifests

    Daily Run, wallet, prizes, earn status and ladder, profiles, push; the supabase/tests cases ported as server tests. The OpenTofu files, the deploy/ overlays and tools/deploy.ps1, checked with tofu validate and a server-side dry run; memory measured on a test VM.

    Rollback: nothing live yet.

  4. 4
    On the VM · you apply

    k3s up, debug builds point at it

    You fill .env.staging and .env.prod, run tofu apply and tools/deploy.ps1 (a step-by-step guide comes with them), and rehearse the rebuild once on staging. Debug builds use the new server for playtests; release builds stay on Supabase.

    Rollback: tools/deploy.ps1 -Rollback for a bad release; tofu destroy removes it all; Supabase is untouched.

  5. 5
    Cutover

    New build on the new server, forced update

    A release build with the new server in its config. Everyone starts fresh: new players, empty boards, no diamonds, and on first launch each phone resets its local save once. Old builds keep talking to Supabase until it is switched off, so friends are told to update. Builds from step 1 onward get the update prompt.

    Rollback: ship a build with the Supabase config again; Supabase is still running.

  6. 6
    Retire · later

    Supabase switched off

    Once no old builds call it (a few weeks), you pause or delete the Supabase project. A later change removes the Supabase client, migrations, Edge Functions and workflows, the GitHub checker (verify-runs.yml) with them. No GitHub fallback runs in the meantime.

    Rollback: until you delete the project, it can be restored.

The one-time reset on the phones

With a fresh start the phone's own save has to start over too, or the first sync would upload old gold and items to the new server.

When

The new build's config names its server (server_id). The save remembers the server it last used. On the first launch where they differ, the phone resets once, before it signs in. A crash halfway simply runs the reset again on the next launch.

Cleared

Gold, owned and worn cosmetics, best scores, rooms reached, earn, streak and ladder state, the cached diamonds and prizes, today's Daily Run state, the queued runs (pending_runs.json), the old session and device key (file and iOS Keychain) and Your runs (runs.json).

Kept

This phone's settings: music, sounds, haptics, reduced flashing, color-blind spikes, large buttons. The leaderboard name, so nobody is asked again.

What the player sees

One card on Home: "Fresh start. Flapjaw has a new server, so scores, coins and items start over." and a Play button. Shown once.
