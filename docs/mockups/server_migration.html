Architecture, today and proposed

Today every server call goes through one class, SupabaseClient: a session plus call_db(name, body), which posts to a Postgres function. The game never reads a table directly. The proposal adds one interface below the existing services, so the screens and services do not change.

sequenceDiagram
  participant P as Phone
  participant SV as Flapjaw server
  participant V as Verifier
  P->>SV: POST /v1/get_daily_run
  SV-->>P: same answer
  P->>SV: POST /v1/start_daily_try

The new server gets its own Daily Run secret, kept in a Kubernetes Secret, so the database never holds it.

  participant P as Phone
  participant SV as Flapjaw server
  P->>P: restore session + device key
  alt access token still valid
    Note over P: done
  else has refresh token
    P->>SV: POST /v1/auth/refresh
    SV-->>P: new tokens
  end

    SV-->>P: session, same player

The device key becomes the real credential; no made-up email address and no separate enroll call. Offline still never makes a new player.

Where it runs: one extra node in your Hetzner Kubernetes cluster

The game gets its own namespace, flapjaw, on a new Hetzner VM joined to the cluster you already run with kubectl. The node is labelled and tainted for the game (flapjaw=true, taint dedicated=flapjaw:NoSchedule); every game pod has the matching nodeSelector and toleration, so the game and your other application never share a machine. The cluster's existing ingress controller and certificates are reused.

The replay check on the server

Rust checks every run

The server links tools/fastsim-rs/sim and replays each run as it arrives, in a background queue. The check already holds the Rust copy tick for tick to GDScript (the parity step).

Godot decides rejections

A run Rust rejects is final only when headless Godot (server/verify_batch.gd) agrees. Rejections are rare, so this costs little, and a parity slip can never hide an honest score.

Older app versions

One frozen sim crate per allowed gameplay version (sim_g24, sim_g25, ...), dispatched on gameplay_version. Retired versions answer "please update".

Same outcomes

ok, rejected, outdated and pending keep today's rules and reasons, so boards behave the same, only faster.

Easier later on our own server: one-time seeds for endless runs, rate limits per player and IP, plausibility checks into a review queue, Play Integrity / App Attest on sign-in.

Rollout

BuildOn the cluster, debug buildsCutoverRetire

With a fresh start there is no data to copy and no freeze. Supabase keeps running untouched until the switch-off, so it is the rollback the whole way.

  1. 1
    Build · no server

    BackendClient interface and an update prompt

    SupabaseClient implements the interface; the config picks the backend. Also a minimum-version answer the game shows as "please update", so this build and later ones can be told to update. Today's builds have no such prompt. No other behaviour change, check passes.

    Rollback: revert the commits.

  2. 2
    Build · local only

    Server skeleton

    Auth with device key, ping, submit_run, get_board, get_run, set_player, the Rust checker. Contract fixtures pass against both the SQL (via tools/db_test.ps1) and the new server.

    Rollback: nothing live yet.

  3. 3
    Build · local only

    The rest of the features, and the manifests

    Daily Run, wallet, prizes, earn status and ladder, profiles, push; the supabase/tests cases ported as server tests. The Kubernetes manifests, checked with a dry run.

    Rollback: nothing live yet.

  4. 4
    On the cluster · you apply

    Namespace on the new node, debug builds point at it

    You add the node and apply the manifests. Debug builds use the new server for playtests; release builds stay on Supabase.

    Rollback: kubectl delete namespace flapjaw; nothing else changes.

  5. 5
    Cutover

    New build on the new server, forced update

    A release build with the new server in its config. Everyone starts fresh: new players, empty boards, no diamonds. Old builds keep talking to Supabase until it is switched off, so friends are told to update. Builds from step 1 onward get the update prompt.

    Rollback: ship a build with the Supabase config again; Supabase is still running.

  6. 6
    Retire · later

    Supabase switched off

    Once no old builds call it (a few weeks), you pause or delete the Supabase project. A later change removes the Supabase client, migrations, Edge Functions and workflows.

    Rollback: until you delete the project, it can be restored.

Open questions for you

Already decided: a fresh start with no data carried over, and hosting on a new node in your Hetzner Kubernetes cluster. Nothing gets built until these are answered too.

  1. LanguageRust (recommended, shares the sim with the server), TypeScript, Go, or something you'd rather maintain yourself?
  2. Ingress and certificatesWhich ingress controller and ingress class does the cluster use (ingress-nginx, Traefik, something else)? Is it cert-manager, and which ClusterIssuer? Which host name should the game's API get?
  3. PostgresDoes the cluster already run Postgres or an operator such as CloudNativePG? If not, is a plain StatefulSet with a nightly dump fine? Where should backups go (an object storage bucket you already have)?
  4. Secrets and backupsWho holds the secrets (database, token key, Daily Run secret, Firebase key)? Plain Kubernetes Secrets you create by hand, or something like Sealed Secrets, SOPS or External Secrets? Who keeps the backups?
  5. How manifests are appliedIs Kustomize with kubectl apply -k fine, or do you use Helm or a GitOps tool for your other application?
  6. Fallback checkerKeep the GitHub + Godot checker running as a fallback until Supabase is switched off?
  7. Board clockKeep the Amsterdam midnight reset for both daily boards?
  8. How far the fresh start goesDiamonds, prizes and boards start empty on the new server. Phones still have their local save (gold, owned items, best score, settings), which the first sync would upload. Keep those local saves, or reset them too with the new build?
